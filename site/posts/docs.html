setup

Build and start a throwaway development instance (no authentication, listens on 127.0.0.1 only):

zig build
./zig-out/bin/zerverg serve --dev --data ./site

For a real deployment, hash a password and put it in the config file (or the ZERVERG_ADMIN_PASSWORD_HASH environment variable):

printf '%s\n' 'my password' | zerverg hash-password
$argon2id$v=19$m=19456,t=2,p=1$...
sudo cp deploy/zerverg.example.zon /etc/zerverg/zerverg.zon
zerverg serve

On first start, zerverg seeds the data directory with this default site. Delete or replace any of it; it is never re-created once site.json exists.

Back it up with tar. Version it with git.

content: posts and pages

An entry is an HTML file. Only the <body> is rendered; metadata travels in <meta> tags:

<title>My post</title>
<meta name="zerverg:date"   content="2026-11-15">
<meta name="zerverg:kind"   content="post">     <!-- post | page -->
<meta name="zerverg:tags"   content="zig,web">
<meta name="zerverg:layout" content="wide">     <!-- optional -->
<meta name="zerverg:slug"   content="my-post">  <!-- for POST -->
  • posts show a title header, appear in lists and feeds of recent posts.
  • pages render as-is and appear in the navigation via <page-links/>.
  • The page with slug index is the home page. Without one, / lists all posts.
  • A page may use a different layout with zerverg:layout; the global style still applies.

Embed a list of entries anywhere in a page:

<zv-entries kind="post" tag="zig" limit="10"></zv-entries>

Slugs are lowercase letters, digits, - and _, up to 64 characters.

layouts (xml)

A layout is a small XML file. The root is <layout> and exactly one <main/> marks where content goes. Layouts are validated on upload: unknown elements, attributes or javascript: links are rejected.

<layout kind="sidebar-right" favicon="media:icon.svg" lang="en">
  <header>
    <logo src="media:me.png" alt="me" size="48"/>
    <site-title/>
    <tagline>notes from the terminal</tagline>
    <nav><link href="/">home</link><page-links/></nav>
  </header>
  <main/>
  <sidebar>
    <section title="search"><search/></section>
    <section title="recent"><recent-posts count="5"/></section>
  </sidebar>
  <footer><text>(c) me</text></footer>
</layout>

URLs may be site paths (/x), anchors, http(s)://, mailto: or media:file.

styles (css)

The active stylesheet is served as /assets/style.css. Target the zv-* classes from the table above. The default theme defines its palette as CSS variables at the top; copy it and change a handful of lines for a new look.

:root { --bg: #1c1e21; --fg: #c5c8c6; --accent: #9ec29a; }

snippets (js)

Snippets are plain JavaScript files, loaded with defer on every page in the order listed in site.json. Inline <script> in content is blocked by the Content-Security-Policy, so behaviour belongs in snippets. The default terminal snippet adds the blinking cursor, copy buttons and the / search shortcut.

Snippets run with the full power of the page. Only enable code you wrote or have read.

media

Upload images (png, jpg, gif, webp, avif, svg, ico) and videos (mp4, webm, ogv) and reference them as media:name.ext:

<img src="media:cat.png" alt="a cat">

Uploads are checked against their file signature, capped per type and by a total quota. SVGs containing scripts are rejected.

versions and rollback

Every upload of a layout, style or snippet with an existing name creates a new version and makes it current. The last history_keep versions are kept:

curl -u admin:pw http://localhost:7080/api/v1/styles/default/versions
[1,2,3]
curl -u admin:pw -X POST \
     "http://localhost:7080/api/v1/styles/default/rollback?version=2"

hardening

On by default, tunable in the config file:

  • login lockout: 5 failures lock an IP out for 15 minutes (login_max_failures, login_lockout_s).
  • rate limit: 20 requests/s per IP, bursts of 120 (rate_limit_per_s, rate_limit_burst; 0 disables).
  • connections: 256 total, 16 per IP, 60 s lifetime, 1000 requests each.
  • bodies: only read after authentication, capped per route; public routes accept none.
  • uploads: text must be UTF-8, layouts must validate, media must match its signature.
  • headers: CSP (public_csp), nosniff, frame denial, strict referrer, permissions and cross-origin policies on every response.
  • sessions: random 256-bit tokens, stored hashed, HttpOnly, SameSite=Strict, scoped to /api; writes need X-Requested-With.

Behind a reverse proxy every client shares the proxy's IP. Raise or disable the per-IP limits in that case.
